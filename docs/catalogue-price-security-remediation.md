# Catalogue Price Security Remediation — post-Gate D

Tracking: #39. This is an **infrastructure-only draft**: no vehicle prices, user data, photos, finance, offline scripts, scheduled refreshes or PhotoHarvest PR #38 are changed.

## Strict trust boundary

- PRs that touch `data/catalogue.json`, `js/catalogue-data.js` or `docs/catalogue-publication-evidence/approval-bundle.json` must change exactly those three paths together. CI checks the diff against the pinned PR base SHA and compares **exact generated bytes** from the trusted base catalogue and identity.
- For these PRs the checked-in `docs/catalogue-publication-evidence/approval-bundle.json` contains version 1, `research`, `researchAuthorisation`, `reviews`, and `authorisation`. Reviewers must independently inspect sources and the full payload; CI verifies signatures, not truth of claims.
- Research and review use **separate Ed25519 signing keys** registered as enabled researchers and approvers in `config/catalogue-publication-approvers.json` (schema version 2). Research identity, complete offer list, base catalogue, identity and research contents are signed by the researcher. The reviewer signs the research-authorisation digest, review manifest and explicit status-promotion allowlist, binding all reviewed evidence.
- Real trust registries remain **empty**. Onboard independently verified public keys via a separately reviewed PR; never add private keys. With empty registries the signature verifier **fails closed when it executes**, but that is not yet full merge protection (see "Dedicated app check rollout" below). Do not bypass the guard via workflow edits or a changed trust registry in the same publication PR.
- Production CLI no longer accepts `--as-of`; source freshness is checked against today's UTC date. Tests still inject a fixed date via the pure function, strictly for deterministic fixtures.
- Gate D still generates files only into a fresh temp directory with `--emit`. The PR guard merely validates the protected-branch diff and never publishes.
- Governance is **solo-maintainer**: there is one human maintainer, there is no review committee, and the main ruleset currently requires **zero** human approving reviews; no additional human reviewers are planned, so this patch deliberately does **not** instruct enabling a human-review requirement that cannot be satisfied. Real catalogue price publication remains disabled until a separately specified and verified solo-maintainer governance model is implemented and reviewed. Green required checks alone must never be read as human approval.
- Any AI-assisted code review is **advisory only**: it is not a human approval and never substitutes for the signed reviewer authorisation or required status checks.
- This guard runs in the separate trusted `pull_request_target` workflow (`.github/workflows/catalogue-publication-trusted.yml`), **not** inside the ordinary `verify` job. The workflow is active on `main` and the check is required on every PR targeting the default branch. Before relying on it, the administrator must complete "Dedicated app check rollout" below, so that a missing, skipped, neutral, stale or non-head-associated check result is never readable as a passing verification. Real price releases stay blocked until then.
- Note: this control is for **pull requests**, not direct-push detection. Branch protections and permission controls must prevent unauthorised pushes or bypasses.

## Security review follow-up — trusted enforcement and deployment prerequisites

The former PR-checkout `verify` job no longer executes publication approval. The new
`.github/workflows/catalogue-publication-trusted.yml` uses `pull_request_target`,
checks out the exact trusted base SHA with persisted credentials disabled,
fetches PR Git objects only as inert data, and executes only **base-branch** code.
It rejects legacy `js/market-catalogue.js` changes until independent approval
rules are designed. In a catalogue publication, only the two generated catalogue
files and signed evidence bundle may differ; no workflow or trust changes are allowed.

The workflow requires the PR to target the repository default branch, verifies
that the event base SHA equals the default-branch `GITHUB_SHA` and that the
checked-out `HEAD` equals that SHA, failing closed on any mismatch; the guard
script re-checks both bindings. These runner-side SHA verifications have run on
real GitHub runners, on both passing and failing PRs.

**IMPORTANT — do not merge on ordinary green checks alone.** The check is
required on **every** PR targeting the default branch, including non-price PRs,
which the guard passes unless they change trust-root files.
The workflow also runs on the `edited` event: if a PR is retargeted away from
the default branch after a passing run, the guard re-runs and fails closed
instead of leaving a stale PASS attached.
GitHub's platform behaviour and VahanaIQ's security requirement must not be
confused. On the platform side, depending on the check mechanism, certain
**skipped or neutral** conclusions can satisfy a required status check — so a
green-looking ruleset alone proves nothing about the trusted guard. On the
VahanaIQ side, catalogue security verification must produce trustworthy
evidence that the correct trusted guard executed against the intended PR
commit and passed the publication policy. Therefore:

- A missing check cannot be assumed to have executed.
- A skipped or neutral result must not be presented as successful catalogue
  security verification.
- A result attached to an earlier PR commit is not adequate evidence for the
  current head, and a check associated with the wrong commit is not adequate
  evidence.
- Status-check rules must be tested for applicability and bypass resistance.
- A trustworthy enforcement mechanism may require additional design beyond
  the existing `pull_request_target` workflow.

The workflow's event-base-SHA and checked-out-HEAD verification steps have run
on real runners, and its results attach to the PR head commit.
GitHub may also restrict `pull_request_target` execution based on PR origin
and approval requirements; never enable a broad trusted event policy without
reviewing the consequences, and never pass credentials or secrets to
untrusted PR code. Real price publication remains prohibited pending
deployment and enforcement verification.

Because the repository is solo-maintained and no additional human reviewers
are planned, this patch deliberately does not instruct enabling an
independent-approval requirement that cannot be satisfied. The administrator
may still consider CODEOWNERS ownership designation for
`config/catalogue-publication-approvers.json`, `.github/workflows/**`,
`scripts/prepare-catalogue-publication.mjs`,
`scripts/verify-catalogue-publication-pr.mjs`, and all canonical pricing
files, and must restrict access to signing-key onboarding and changes to this
workflow. The connected integration cannot change the repository ruleset.

No reviewer or researcher keys have been onboarded. Until the trusted check
is confirmed required and a separately specified and verified solo-maintainer
governance model is implemented, real catalogue price publication is disabled.

## GitHub Actions policy and deployment check

The privileged workflow deliberately checks out the default branch's event SHA
rather than an arbitrary PR base branch. The first step rejects PRs targeting
other branches. Under GitHub's revised Actions policy, **enforced at the latest on
2 December 2026**, `pull_request_target` execution may be restricted; the
repository administrator must
check the Actions event policy before treating this as a reliable required check.
See https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target .
Any missing, skipped, neutral, stale or non-head-associated check must keep
actual price publication blocked: on GitHub's platform side certain skipped or
neutral conclusions can satisfy a required check, so VahanaIQ's own
requirement is trustworthy evidence that the correct guard executed against
the intended PR head and passed. Never enable a broad trusted event policy
without reviewing the security
consequences, and never pass credentials or secrets to untrusted PR code. Merge
enforcement is **not proven** until the trusted check is a required status check
that cannot be bypassed or silently skipped; real price publication remains
disabled in the meantime. The full solo-maintainer governance statement lives in `SECURITY.md`.

## Dedicated app check rollout

A ruleset matches a required check by name and source, and GitHub Actions is the
shared source for every workflow in the repository. Only a source that pull
request workflows cannot reproduce makes a missing guard result fail closed, so
the check moves to the dedicated app `vahanaiq-trusted-check-publisher` (5560876).
The Actions job keeps its name during rollout, so either source can be required.

### Maintainer steps

Create the environment **before** merging the workflow change. A workflow can
create a missing environment by naming it, and that environment would have no
branch rule.

1. In your account's **Settings → Developer settings → GitHub Apps**, click
   **Edit** next to the app, then **Key pairs → New key**. Use a new key rather
   than reusing an existing one. Confirm the app has `Checks: write` and is
   installed only on this repository.
2. Go to **Settings → Environments → New environment** and name it
   `catalogue-publisher`.
3. Under **Deployment branches and tags**, choose **Selected branches and tags**
   and add only `main`.
4. Add the environment secret `CHECK_PUBLISHER_KEY`, then delete the downloaded
   key file.
5. Merge the workflow change. Check 1 below must pass on the next PR.
6. In the repository's **Settings**, under "Code, planning, and automation", open
   **Rulesets → Rulesets → Protect Main Branch**. Under the required status checks
   rule, change the source of `catalogue-publication-trusted` from GitHub Actions
   to `vahanaiq-trusted-check-publisher`, then click **Save changes**. GitHub only
   offers an app that has recently submitted a check run, which check 1 provides.
7. Run checks 2 to 6 below, then record the result here and in `SECURITY.md`.

To roll back, set the source in step 6 back to GitHub Actions.

### Rollout checks

Each uses a temporary PR that is closed without merging.

1. **Normal PR:** a non-price PR gets a `success` check from app 5560876 on its
   head commit, and can merge.
2. **Trust-root PR:** a PR that adds a workflow gets a `failure` check from the
   app, and is blocked.
3. **Spoof:** on a PR that adds a same-named job, the job's success under GitHub
   Actions does not unblock the PR.
4. **Secret access:** a job in a PR's own workflow that names
   `catalogue-publisher` cannot read the key.
5. **Guard absent:** with the trusted workflow briefly disabled, a new PR gets no
   app check and is blocked. Re-enable the workflow straight away.
6. **Replacement:** retargeting a PR away from `main` and back publishes failure
   then success on the same commit. Confirm the merge state follows the newest
   result, and that a newer failure replaces an older success.

### Changing trust-root files

The guard rejects changes to `.github/`, `config/`, the verifier and publisher
scripts, `js/vehicle-validation.js` and `data/identity.json`. Nothing automated
can approve these. To merge one after reviewing it:

1. Remove `catalogue-publication-trusted` from the ruleset's required checks.
2. Merge that PR, leaving all other required checks in place.
3. Add the check back with the app as its source, straight away.

The ruleset history records each change. No permanent bypass actor is used,
because one would also let a price PR skip the check.
